Создай интерактивный образовательный симулятор в стиле GoPractice и Яндекс Практикума.

Задача: сделать не обычный курс с лекциями, а продуктовый симулятор, где пользователь проходит сценарии, принимает решения, решает задачи, получает автоматическую обратную связь и видит прогресс.

Приложение должно быть построено как интерактивный тренажёр с frontend- и mock-backend-логикой.

## Общая механика продукта

Пользователь попадает в симуляцию работы внутри продуктовой команды. Каждый модуль — это отдельный рабочий кейс. Внутри кейса есть контекст, задача, данные, варианты решений, проверка ответа, обратная связь и следующий шаг.

Симулятор должен работать по принципу:

1. Пользователь читает вводный контекст.
2. Получает рабочую ситуацию.
3. Анализирует данные, таблицы, метрики или описание проблемы.
4. Выполняет задание.
5. Отправляет ответ.
6. Система автоматически проверяет ответ.
7. Пользователь получает feedback:

   * что правильно;
   * что ошибочно;
   * почему;
   * как мыслить правильно;
   * какой следующий шаг.
8. После успешного прохождения открывается следующий экран или следующий шаг сценария.

Сделай следующие экраны:

1. Экран выбора симулятора
2. Карта курса / карта модулей
3. Экран модуля
4. Экран урока / шага сценария
5. Экран задачи
6. Экран с данными / таблицей / метриками
7. Экран выбора решения
8. Экран проверки ответа
9. Экран обратной связи
10. Экран результата по модулю
11. Экран общего прогресса
12. Личный кабинет пользователя
13. Настройки профиля

## Структура симулятора

Каждый модуль должен состоять из нескольких шагов:

* context — вводная ситуация;
* theory — короткое объяснение;
* task — практическое задание;
* decision — выбор решения;
* check — автоматическая проверка;
* feedback — объяснение результата;
* next_step — переход дальше.

## Типы заданий

Добавь разные типы заданий:

1. Single choice — выбор одного правильного ответа.
2. Multiple choice — выбор нескольких правильных ответов.
3. Text answer — короткий текстовый ответ.
4. Metric analysis — анализ метрик.
5. Funnel analysis — анализ воронки.
6. Retention analysis — анализ удержания.
7. Product decision — выбор продуктового решения.
8. Prioritization — расстановка гипотез по приоритету.
9. Case simulation — решение бизнес-кейса.
10. Data interpretation — вывод по данным.

## Логика проверки ответов

Сделай mock-backend validation engine.

Он должен проверять:

* выбранный вариант ответа;
* несколько выбранных вариантов;
* текстовый ответ по ключевым словам;
* правильность выбранной метрики;
* корректность продуктового вывода;
* завершение шага;
* статус прохождения модуля.

Для каждого задания должны быть состояния:

* not_started;
* in_progress;
* submitted;
* correct;
* incorrect;
* completed.

## Feedback-механика

Если ответ правильный, показывай:

* “Верно”
* короткое объяснение;
* почему это решение работает;
* кнопка “Продолжить”.

Если ответ неправильный, показывай:

* “Не совсем”
* что именно не так;
* подсказку;
* возможность попробовать ещё раз;
* кнопку “Попробовать снова”.

Если пользователь ошибся несколько раз, показывай более подробное объяснение и кнопку “Показать разбор”.

## Механика прогресса

Сохраняй прогресс пользователя:

* текущий модуль;
* текущий шаг;
* завершённые задания;
* процент прохождения;
* количество правильных ответов;
* количество попыток;
* время прохождения;
* открытые и закрытые модули.

Используй localStorage или mock-backend state.

## Визуальная логика

Сделай интерфейс современным, чистым, образовательным и продуктовым.

Стиль: B2B SaaS + образовательная платформа + интерактивный симулятор.

Важно: интерфейс должен ощущаться не как обычный курс, а как рабочая среда продуктового менеджера.

Используй следующие UI-паттерны:

* карточки задач;
* блоки контекста;
* панели с метриками;
* таблицы данных;
* чатовые вставки от “команды”;
* decision cards;
* feedback cards;
* progress tracker;
* locked/unlocked modules;
* step-by-step flow.

## Mock data

Добавь демо-кейс:

Название симулятора: “Product Manager Simulator”

Модуль 1: “Анализ онбординга”

Ситуация:
Ты продуктовый менеджер в приложении для обучения. Команда видит, что пользователи регистрируются, но плохо доходят до первого целевого действия. Нужно найти проблему в онбординге и предложить решение.

Данные:

* Visitors: 10 000
* Registration started: 4 200
* Registration completed: 3 100
* Onboarding started: 2 900
* Onboarding completed: 1 350
* First key action: 620

Задача:
Определи, на каком этапе самый большой drop-off и какое продуктовое действие нужно проверить первым.

Правильная логика:
Самый проблемный этап — прохождение онбординга. Нужно проверить длину онбординга, непонятные шаги, friction points, обязательные поля и value proposition до завершения онбординга.

Добавь варианты ответа:

1. Увеличить рекламный бюджет
2. Проверить и сократить онбординг
3. Добавить больше push-уведомлений
4. Изменить цвет кнопки регистрации

Правильный ответ:
Проверить и сократить онбординг.

Feedback:
Проблема не в привлечении и не только в регистрации. Самый сильный провал происходит внутри онбординга: из 2 900 пользователей до конца доходят только 1 350. Значит, сначала нужно искать friction внутри сценария: количество шагов, сложность вопросов, непонятную ценность, обязательные поля и отсутствие быстрого первого результата.

## Техническая логика

Собери приложение на React.

Используй компонентную архитектуру:

* App
* CourseMap
* ModulePage
* LessonStep
* TaskCard
* MetricsTable
* AnswerOptions
* FeedbackPanel
* ProgressBar
* ProfilePage
* SettingsPage

Создай mock-backend через локальный объект данных.

Сохраняй пользовательский прогресс в localStorage.

Все задания, шаги, правильные ответы и feedback должны храниться в структуре данных, а не быть захардкожены прямо в UI.

Сделай так, чтобы позже можно было легко добавить новые модули и задания через JSON-конфиг.

## Главное правило

Не делай просто лендинг курса. Сделай именно интерактивный симулятор: сценарий, задача, действие пользователя, автоматическая проверка, feedback, прогресс и переход к следующему шагу.
